# Fluff iOS 성능 개선 및 실기기 측정 리포트

- 작성일: 2026-11-10
- 대상: 홈 3D 방의 렌더링 빈도, 고정 가구 처리, 메모리·발열
- 상태: 구현·빌드·기능 검증 완료, 변경 전후 실기기 장시간 측정 완료
- 원본 데이터: [Release 실기기 측정 JSON](../scripts/memory-results/2026-11-10-adaptive-rendering.json)

## 1. 결과 요약

홈에서 대기할 때는 30fps, 조작할 때는 60fps를 목표로 렌더링하도록 변경했다. 같은 형상과 재질을 사용하는 고정 가구 부품은 함께 처리하도록 묶었다.

실제 iPhone에서 변경 전후 각각 11분 이상 측정한 결과, **CPU 사용량 중앙값은 약 39.8% 감소**했다. 종료 시 메모리는 **382.0 → 376.8MiB**, Metal 할당 메모리는 **191.3 → 182.7MiB**로 감소했다.

다만 메모리 감소 폭은 제한적이며, 개선 버전의 조작 구간에는 일시적인 메모리 상승도 있었다. **두 실험 모두 iOS 발열 상태가 `serious`였으므로, 발열 문제가 해결됐다고 판단할 수 없다.** 기존에 관찰된 약 600MB 사용량도 이번 측정과 조건이 달라 직접 비교할 수 없다.

## 2. 배경과 작업 범위

실제 iPhone에서 앱을 오래 실행할 때 강한 발열과 약 600MB의 메모리 사용이 보고됐다. 이번 작업은 화면 품질을 최대한 유지하면서 다음 세 항목을 구현하고 검증하는 범위로 진행했다.

1. 홈 대기 시 30fps, 조작 시 60fps로 렌더링 빈도 조절
2. 반복되는 고정 가구 부품을 묶어 렌더링 처리 부담 감소
3. Metal 셰이더를 포함한 Release 빌드로 실제 기기에서 10분 이상 비교 측정

이번 기준 버전에는 앞서 적용한 가구 텍스처·재질 정리 등의 최적화가 이미 포함되어 있다. 따라서 아래 수치는 최초의 800MB 또는 600MB 상태와 비교한 결과가 아니라, **이번 변경 직전 버전과 비교한 결과**다. 이전 실험은 [가구 리소스 개선 측정 기록](../scripts/memory-results/2026-11-10-furniture-resources.json)에 별도로 보관했다.

## 3. 구현 내용

### 3.1. 홈 렌더링 빈도 조절

홈은 `RealityRenderer`와 `MTKView`를 사용하는 구조로 변경했다. 편집·미리보기 화면은 기존 `ARView` 경로를 유지한다.

| 상황 | 동작 |
| --- | --- |
| 홈 대기 | 목표 30fps |
| 터치·드래그·카메라 조작 | 목표 60fps |
| 조작 종료 | 짧은 유지 시간 이후 30fps로 복귀 |
| 앱 비활성화 또는 뷰가 화면에서 분리됨 | 홈 렌더링 일시 정지 |
| GPU 작업 대기 | 최대 두 프레임까지만 동시에 처리 |

인형 선택·이동을 위한 좌표 변환과 충돌 검사, 집중 화면 배경에 사용하는 방 캡처도 새 렌더러에 연결했다. 목표 프레임 수는 기기의 부하와 발열 상태에 따라 실제 완료 프레임 수와 다를 수 있다.

관련 코드: [RoomRenderView.swift](../Malrang/Services/RoomRenderView.swift), [RoomSceneView.swift](../Malrang/Features/Room/RoomSceneView.swift)

### 3.2. 고정 가구 부품 묶기

같은 메시 형상과 재질을 사용하는 부품을 `MeshInstancesComponent`로 묶었다. 정점 데이터를 부품마다 복제하지 않고, 각 부품의 크기·위치·회전 정보를 전달한다.

- 원래 천 질감 좌표와 부품별 변환을 유지한다.
- 움직이는 침구가 있는 침대는 묶기 대상에서 제외한다.
- 사용자 사진과 별도 처리가 필요한 창문 하늘 등은 대상에서 제외한다.
- 테스트한 방에서 모델 구성요소가 **620개에서 552개로 68개 감소**했다.

개발 중 임시 `MeshResource` 객체의 주소를 식별자로 사용하면 서로 다른 형상이 같은 그룹에 들어갈 수 있는 오류를 발견했다. 실제 형상 데이터를 비교하도록 수정했고, 서로 다른 형상이 섞이지 않는지와 복제 후 변환이 유지되는지를 회귀 검증에 추가했다.

모델 구성요소 감소는 확인했지만, GPU의 실제 draw call 수를 직접 캡처하지는 않았다.

관련 코드: [FurnitureInstances.swift](../Malrang/Features/Room/FurnitureInstances.swift), [SceneFactory.swift](../Malrang/Features/Room/SceneFactory.swift)

### 3.3. Metal 처리와 측정 기록

기존 블룸 처리를 새 렌더러에서도 사용할 수 있도록 연결했다. 블룸 버퍼 할당에 실패하는 경우에는 서로 다른 색상 포맷 사이에서도 복사할 수 있는 Metal 커널을 사용하도록 보완했다.

Release 빌드에서도 실행 인자로 활성화할 수 있는 로컬 진단 기능을 추가했다. 약 10초 간격으로 메모리, CPU, 렌더링 완료 횟수, 발열 상태와 장면 구성을 기록한다. 진단 기능은 저장된 인형과 방 배치를 수정하지 않는다.

관련 코드: [CozyBloom.swift](../Malrang/Features/Room/CozyBloom.swift), [CozyFabric.metal](../Malrang/Resources/CozyFabric.metal), [RoomPerformanceAudit.swift](../Malrang/App/RoomPerformanceAudit.swift)

## 4. 측정 조건

| 항목 | 조건 |
| --- | --- |
| 기기 | 실제 iPhone 17 Pro |
| 운영체제 | iOS 26.6.2 |
| 빌드 | Release, 디버거 연결 없이 실행 |
| 방 구성 | 같은 저장된 방, 인형 3개·가구 10개 |
| 시나리오 | 매분 처음 약 10초 동안 카메라 이동, 나머지 시간 대기 |
| 변경 전 실행 | 기존 렌더러, 가구 묶기 비활성화 |
| 변경 후 실행 | 새 렌더러, 가구 묶기 활성화 |
| 실행 순서 | 변경 전 측정 후 변경 후 측정, 각 1회 |
| 측정 시간 | 변경 전 662.9초 / 변경 후 678.9초 |
| 실제 렌더링 조건 | 두 실행 모두 발열 제한에 따라 스케일 1, 블룸 비활성화 |
| 일반 품질 설정 | 기존 정책 유지: 일반 상태에서 스케일 최대 1.5와 블룸 사용 |

메모리는 `task_vm_info.phys_footprint`, Metal 메모리는 `MTLDevice.currentAllocatedSize`를 사용했다. 단위는 **MiB = 1,048,576바이트**다. Metal 할당 메모리는 별도의 지표이므로 물리 메모리에 더해 총사용량으로 계산하지 않는다.

CPU 비율은 **CPU 한 코어를 100%로 보는 기준**이다. 아래 중앙값과 범위는 초기 로딩 영향을 줄이기 위해 실행 후 60초 이후 표본으로 계산했다.

## 5. 측정 결과

| 지표 | 변경 전 | 변경 후 | 해석 |
| --- | ---: | ---: | --- |
| CPU 사용량 중앙값 | 37.40% | 22.51% | 약 39.8% 감소 |
| 메모리 중앙값 | 381.88MiB | 372.63MiB | 약 9.25MiB 감소 |
| 종료 시 메모리 | 382.03MiB | 376.81MiB | 약 5.22MiB 감소 |
| 메모리 표본 범위 | 380.47–382.27MiB | 368.31–395.74MiB | 개선 후 조작 구간의 일시적 상승 존재 |
| 종료 시 Metal 할당 메모리 | 191.31MiB | 182.70MiB | 약 8.61MiB 감소 |
| 모델 구성요소 | 620개 | 552개 | 68개 감소 |
| iOS 발열 상태 | serious(2) | serious(2) | 단계 개선 확인 못 함 |
| 기록된 렌더링 오류 | 없음 | 없음 | 측정 구간 내 오류 없음 |

개선 버전에서 대기 구간의 약 30fps와 조작 구간의 약 58.6fps 표본을 확인했다. 전체 조작 구간에서 항상 60fps를 유지했다고 해석해서는 안 된다.

기준 버전의 프레임 지표는 `SceneEvents.Update` 호출 횟수이고, 개선 버전은 GPU 프레임 제출·표시 명령의 완료 횟수다. **서로 같은 계측 방식이 아니므로 전후 FPS를 직접 비교하거나 디스플레이의 실제 주사율로 해석하지 않는다.**

메모리는 조작 중 상승한 뒤 대기 중 다시 낮아지는 양상을 보였다. 다만 표본 간격 사이의 순간 최대값은 기록하지 않았으며, 이 결과만으로 메모리 누수가 없다고 확정할 수 없다.

개인 인형 이미지와 실제 방 캡처는 이 리포트에 첨부하지 않았다. 측정 종료 후 iPhone은 진단 인자 없는 일반 실행 상태로 복원했다.

## 7. 한계와 남은 확인 사항

**확인된 개선은 CPU 처리 부담 감소와 제한적인 메모리 감소다. 발열 해결과 600MB 문제의 완전한 해소는 미확인 상태다.**

- 전후 각 1회 측정이며, 실행 순서에 따른 기기 온도·백그라운드 부하 영향을 분리하지 못했다.
- 두 실행 모두 발열 제한이 적용됐다. 일반 품질 설정에서의 메모리와 기존 600MB 관찰값은 별도로 재측정해야 한다.
- 표면 온도와 소비 전력은 측정하지 않았다. CPU 사용량 감소를 온도 하락으로 환산할 수 없다.
- GPU 실행 시간과 실제 draw call 수는 계측하지 않았다.
- 이번 장시간 측정은 홈 중심이다. 여러 화면을 반복 방문할 때의 메모리 누적 여부는 별도 검증이 필요하다.

다음 검증은 아직 수행하지 않았으며, 우선순위는 다음과 같다.

1. 기기가 충분히 식은 상태에서 화면 밝기·충전·저전력 모드 조건을 맞추고 전후 반복 측정하기
2. 일반 품질 설정에서 홈 → 집중 → 인형 만들기 → 홈을 반복하며 리소스 해제와 최대 메모리 확인하기
3. Instruments로 조명·그림자·천 재질의 GPU 시간을 측정하고 가장 큰 비용부터 줄이기
4. 추가 기기에서도 30/60fps 전환과 장시간 발열·메모리 검증하기

## 8. 재측정 방법

실제 기기용 Release 빌드를 설치한 뒤 아래 실행 인자로 각 시나리오를 별도 실행한다. Xcode 실행 옵션에 인자를 지정하는 경우 디버거 연결은 해제한다.

**기준 측정 인자**

```text
--legacy-room-renderer
--unbatched-furniture
--room-performance-audit
```

**개선 측정 인자**

```text
--room-performance-audit
```

기본 측정 시간은 660초이며, `--performance-seconds=660`으로 명시할 수도 있다. 결과는 앱 데이터 컨테이너의 `Documents/room-performance-audit.json`에 기록된다. 다음 실행에서 같은 파일이 갱신되므로 각 실행이 끝난 뒤 결과를 별도로 보관한다.

`finished: true`, 실제 기록 시간 600초 이상, 앱 활성 상태, 동일한 인형·가구 수, 발열 상태와 렌더링 스케일을 확인한 뒤 비교한다. 측정 중 탭을 바꾸거나 다른 앱을 사용한 기록은 같은 시나리오의 비교에서 제외한다. 측정 후 진단 인자를 제거하고 앱을 다시 실행한다.
